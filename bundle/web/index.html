Weighted to your project

Not every benchmark matters equally, and what matters depends on the code. Three mechanisms handle that, all set in a small project.toml that humans own.

1Weights from questions

Answer eight questions (data sensitivity, audience, lifespan, failure impact, team, change rate, delivery, scale) or start from a preset (default, service, web_app, library, oss_library, cli, internal_tool, prototype). Each answer moves specific weights; --explain shows why.

2Gates

Correctness and Security always, plus whatever your answers add. A failed gate caps the overall score: a weighted average can't make up for a security hole.

3Criticality zones

Mark hot code (money, auth, data writes) and cold code (scripts, examples). Problems count one severity higher in hot zones, and hot-zone fixes are ranked first.

# 1. Describe the project (keep this file outside the repo)
python3 SUITE_DIR/tools/gradekit.py init --preset service --name orders-api \
    --answer data_sensitivity=financial --out project.toml

# 2. Edit project.toml: answers, hot/cold zones, targets. Then check the result:
python3 SUITE_DIR/tools/gradekit.py resolve --config project.toml

# 3. Ask about any weight
python3 SUITE_DIR/tools/gradekit.py resolve --config project.toml --explain A4

The loop

The setup that makes rising scores mean better code. Full details →

  1. ConfigureDescribe the project once in project.toml: preset, answers, hot and cold zones.
  2. GradeThree independent graders audit the same commit, each in a fresh sandbox.
  3. Checkgradekit validate and verify-evidence reject bad reports.
  4. Consensusgradekit stability takes the median and flags unstable benchmarks.
  5. Redactgradekit redact strips hidden-check results before sharing.
  6. DecideHumans answer decision questions and record accepted findings.
  7. ImproveImprovers follow gradekit's ranked priorities: failed gates and hot-zone problems first, and stop at each target.
  8. GuardPR quick mode plus gradekit diff --fail-on-regression on every change.
