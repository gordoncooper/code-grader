Three tools, nothing to install

They run the suite's own code in your browser. Your files and reports stay on your computer and aren't uploaded anywhere.

1 · Once per project

Set up a project

Pick a preset, answer eight questions, and mark critical code. Weights and gates update live, and you download project.toml.
2 · Every run

Start a run

Choose the job, where things live and how results come back. You get the exact prompt to paste into your agent.
3 · Every report

Review a report

See where the code stands, answer decision questions, compare with last time, and check the grader's citations.

How a cycle works

One central grading repo holds a folder per project: its settings, your decisions, and one dated folder per report. Graders add reports by pull request; you can also work with plain local files. Full walkthrough →

  1. Set up, onceDescribe the project with Set up a project, and add the file to your grading repo under projects/<name>/.
  2. GradeGet a grader prompt from Start a run and paste it into any agent, cloud or local. The report arrives as a pull request to the grading repo, or as files.
  3. Review and decideOpen it in Review a report, which also compares it with the previous report. Answer the decision questions and merge.
  4. ImproveAn improver agent works down the ranked priorities and opens a pull request.
  5. GuardA pull-request check on each change fails anything that makes the code worse.

Weighted to your project

Not every benchmark matters equally, and what matters depends on the code. Three mechanisms handle that, all set in project.toml, which humans own.

1Weights from questions

Answer eight questions (data sensitivity, audience, lifespan, failure impact, team, change rate, delivery, scale) or start from a preset (default, service, web_app, library, oss_library, cli, internal_tool, prototype). Each answer moves specific weights.

2Gates

Correctness and Security always, plus whatever your answers add. A failed gate caps the overall score: a weighted average can't make up for a security hole.

3Criticality zones

Mark hot code (money, auth, data writes) and cold code (scripts, examples). Problems count one severity higher in hot zones, and hot-zone fixes are ranked first.
